# release-process Specification

## Purpose
Закрепляет процедуру выпуска ветки с изменённым поведением в репозитории:
критерий готовности ветки к слиянию, цель и содержание pull request,
блокирующие проверки, способ слияния, судьба тегов и ветки. Существует,
чтобы подготовка к слиянию не зависела от индивидуального решения
и повторялась от выпуска к выпуску.

## Requirements

### Requirement: Критерий готовности ветки к слиянию
Ветка SHALL считаться готовой к созданию pull request только после
успешного локального прогона всех проверок проекта: проверки форматирования
(`ruff format --check .`), линтера (`ruff check .`), тестов (`pytest`) и
валидации спецификаций (`openspec validate --all --strict`), выполненных
версиями инструментов, закреплёнными в `requirements-dev.txt`. Проверки
SHALL выполняться до отправки коммитов в remote.

#### Scenario: Все проверки зелёные
- **WHEN** в рабочем каталоге ветки успешно отрабатывают проверка
  форматирования, линтер, тесты и валидация спецификаций
- **THEN** ветка готова к отправке коммитов и созданию pull request

#### Scenario: Хотя бы одна проверка красная
- **WHEN** локальный прогон даёт ошибку форматирования, линтера, тестов или
  валидации спецификаций
- **THEN** ветка не отправляется в remote и pull request не создаётся до
  устранения ошибки

### Requirement: Цель слияния — ветка master
Pull request SHALL создаваться из ветки с изменениями в ветку `master` —
целевую ветку репозитория и цель триггера CI по push. Создание отдельной
ветки `main` параллельно `master` или переименование `master` в `main` при
подготовке выпуска MUST NOT выполняться.

#### Scenario: Ветка готова к выпуску
- **WHEN** ветка с изменениями достигла критерия готовности
- **THEN** pull request создаётся с базой `master` и head — ветка с
  изменениями

### Requirement: Слияние только при зелёном конвейере
Слияние pull request SHALL выполняться только после успешного прохождения
всех шагов CI на текущем head pull request. Способ обхода проверок
(force-merge, слияние при красном прогоне, отключение шагов конвейера ради
этого выпуска) MUST NOT применяться; выявленная проверкой проблема
устраняется в ветке отдельным коммитом.

#### Scenario: Прогон CI зелёный
- **WHEN** все шаги конвейера завершились успешно
- **THEN** pull request готов к слиянию

#### Scenario: Прогон CI красный
- **WHEN** шаг конвейера завершился ошибкой
- **THEN** слияние не выполняется, проблема устраняется в ветке, после чего
  конвейер запускается повторно

### Requirement: Merge-коммит как способ слияния
Слияние SHALL выполняться merge-коммитом с сохранением отдельных коммитов
ветки. Squash-merge и rebase-merge MUST NOT применяться: каждый коммит
ветки содержит отдельное изменение с собственным сообщением и архивом
OpenSpec change'а, и схлопывание истории делает выпуск невоспроизводимым.

#### Scenario: Слияние выполнено
- **WHEN** выполняется слияние pull request в `master`
- **THEN** в `master` появляется merge-коммит с двумя родителями, а все
  коммиты ветки сохраняются в истории без изменения

### Requirement: Содержание pull request
Описание pull request SHALL содержать назначение изменений (что нового для
пользователя), перечень входящих коммитов либо архивированных OpenSpec
change'ей, указание выполненных проверок и результат их прогона, а также
явное указание, что поведение несовместимых изменений не требуется либо
требуется с описанием.

#### Scenario: Pull request открыт
- **WHEN** создаётся pull request с изменениями
- **THEN** его описание содержит назначение изменений, перечень коммитов
  или архивированных change'ей, состав выполненных проверок и уровень
  совместимости

### Requirement: Версия фиксируется в ветке до создания pull request
Архивирование OpenSpec change'а, входящего в выпуск, и повышение версии в
файле `VERSION` SHALL выполняться в выпускаемой ветке до создания pull
request, чтобы `master` получил версию тем же слиянием.

#### Scenario: Версия входит в выпуск
- **WHEN** change уровня «исправление» архивируется в выпускаемой ветке при
  версии `1.0.3`
- **THEN** в коммите ветки `VERSION` содержит `1.0.4`, и pull request
  включает этот коммит

### Requirement: Теги и релизы не создаются
В рамках выпуска теги и GitHub Release SHALL NOT создаваться, если это не
запрошено отдельно. Версия проекта распространяется только файлом `VERSION`
в репозитории.

#### Scenario: Выпуск завершён
- **WHEN** pull request слит в `master`
- **THEN** в репозитории не появляется новых тегов и GitHub Release

### Requirement: Ветка удаляется после слияния
Ветка, слитая в `master`, SHALL удаляться на remote после слияния; локальная
ветка MAY оставаться.

#### Scenario: Слияние подтверждено
- **WHEN** merge-коммит появился в `master`
- **THEN** remote-ветка с изменениями удаляется
