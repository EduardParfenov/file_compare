# application-logging Specification

## Purpose

Журналирование приложения, чтобы проглоченные сбои и деградации были
диагностируемы по журналу, а не по догадкам, и чтобы содержимое документов и
секреты в журнал не попадали.

## Requirements

### Requirement: Настройка журналирования через конфигурацию
Уровень журнала MUST задаваться переменной окружения, а не значением в коде.
Незаданное или недопустимое значение MUST приводить к значению по умолчанию,
а не к отказу приложения при запуске. Журнал MUST писаться в стандартный поток
вывода и MUST NOT требовать файлов, внешних сервисов и дополнительных
зависимостей.

#### Scenario: Уровень задан переменной окружения
- **Дано** переменная окружения задаёт уровень журнала
- **Когда** приложение запускается
- **То** записи ниже заданного уровня не попадают в журнал

#### Scenario: Уровень не задан или недопустим
- **Дано** переменная окружения отсутствует или содержит неизвестный уровень
- **Когда** приложение запускается
- **То** приложение работает с уровнем по умолчанию

### Requirement: Содержимое записи журнала
Запись MUST содержать место (модуль и функция), операцию и причину сбоя в
форме, позволяющей понять, что именно не удалось. Запись MUST NOT содержать
текст блоков документов, содержимое изображений, адреса и ключи внешних
сервисов, а также текст промптов и ответов модели целиком. Идентификаторы
(имя задачи, номер страницы) в записи допустимы.

#### Scenario: Запись о пропущенном изображении
- **Дано** при конвертации PDF изображение не удалось закодировать
- **Когда** пишется запись журнала
- **То** в записи указаны модуль, операция и причина
- **И** байты изображения в записи отсутствуют

#### Scenario: Запись о сбое модели
- **Дано** модель вернула сетевую ошибку при чтении страницы
- **Когда** пишется запись журнала
- **То** в записи указана причина сбоя и номер страницы
- **И** адрес сервиса и ключ API в записи отсутствуют

### Requirement: Журналирование проглоченных сбоев
Каждый сбой, который приложение намеренно проглатывает и продолжает работу,
MUST быть записан в журнал. Молчащее продолжение без записи допустимо только
там, где сбой ожидаем по построению и не меняет результат. Отсутствие записи
о проглоченном сбое MUST считаться дефектом.

#### Scenario: Модель недоступна при чтении страниц
- **Дано** модель чтения страниц недоступна
- **Когда** страница не прочитана и разметка помечена как непрочитанная
- **То** причина недоступности записана в журнал

#### Scenario: Классификатор недоступен
- **Дано** chat-модель классификатора вернула ошибку
- **Когда** приложение переходит к алгоритмическим меткам
- **То** причина сбоя записана в журнал

#### Scenario: Сбой без последствий для результата
- **Дано** повреждённая страница не помешала определить наличие текстового слоя
- **Когда** страница пропущена и проверка продолжается
- **То** пропуск зафиксирован в журнале

### Requirement: Журнал не влияет на результат сравнения
Журналирование MUST NOT изменять формат ответов API, состав результата
задачи и тексты, показываемые пользователю. Сбой записи в журнал MUST NOT
прерывать выполнение задачи.

#### Scenario: Сравнение выполняется как прежде
- **Дано** журналирование включено
- **Когда** выполняется сравнение двух документов
- **То** результат задачи не отличается от результата при выключенном
  журналировании

#### Scenario: Журнал недоступен
- **Дано** запись в журнал завершилась ошибкой
- **Когда** выполняется сравнение документов
- **Когда** приложение продолжает работу и результат задачи формируется
