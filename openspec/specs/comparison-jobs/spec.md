# comparison-jobs Specification

## Purpose

Асинхронное выполнение сравнения документов с этапными статусами и опросом
состояния, чтобы пользователь видел ход обработки, а не «зависшую»
страницу.

## Requirements

### Requirement: Запуск задачи сравнения
Система SHALL предоставлять эндпоинт `POST /api/compare`, принимающий JSON
с идентификаторами двух загруженных файлов, создающий задачу сравнения и
возвращающий её идентификатор `job_id`. Обработка MUST выполняться
асинхронно: ответ на запрос не дожидается завершения сравнения. Запрос с
неизвестным идентификатором файла MUST отклоняться с кодом 404, запрос
без идентификаторов — с кодом 400.

#### Scenario: Успешный запуск сравнения
- **Дано** загружены два файла с идентификаторами `id1` и `id2`
- **Когда** клиент отправляет `POST /api/compare` с `{"upload_id_1": "id1", "upload_id_2": "id2"}`
- **То** ответ имеет код 202 и содержит `job_id`
- **И** задача сравнения создана и выполняется асинхронно

#### Scenario: Запуск с неизвестным файлом
- **Когда** клиент отправляет `POST /api/compare` с несуществующим `upload_id`
- **То** ответ имеет код 404 и JSON с полем `error`

#### Scenario: Запуск без идентификаторов файлов
- **Когда** клиент отправляет `POST /api/compare` без `upload_id_1` или `upload_id_2`
- **То** ответ имеет код 400 и JSON с полем `error`

### Requirement: Этапные статусы задачи
Задача сравнения SHALL проходить этапы «Конвертация файлов...» → «Поиск
различий...» → «Анализ через LLM...» и завершаться статусом «готово» либо
«ошибка». Система SHALL предоставлять эндпоинт `GET /api/jobs/<job_id>`,
возвращающий текущий статус задачи, ключ текущего этапа (`stage`:
`converting` / `diffing` / `llm`), сообщение текущего этапа, а при
завершении — результат сравнения (блоки обоих документов и классифицированные
различия) либо сообщение об ошибке. Результат завершённой задачи MUST
включать поле `fragments_count` — число различающихся фрагментов,
переданных на классификацию. Запрос несуществующей задачи MUST
возвращать код 404.

#### Scenario: Опрос задачи в процессе обработки
- **Дано** задача сравнения запущена и находится на этапе поиска различий
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ содержит статус «в обработке», ключ этапа `diffing` и сообщение «Поиск различий...»

#### Scenario: Получение завершённой задачи
- **Дано** задача сравнения успешно завершена
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ содержит статус «готово»
- **И** результат со структурой обоих документов и классами различий для каждого фрагмента
- **И** результат содержит поле `fragments_count` с числом различающихся фрагментов

#### Scenario: Задача завершилась ошибкой
- **Дано** задача сравнения завершилась ошибкой конвертации
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ содержит статус «ошибка» и сообщение об ошибке

#### Scenario: Запрос несуществующей задачи
- **Когда** клиент запрашивает `GET /api/jobs/<несуществующий_id>`
- **То** ответ имеет код 404 и JSON с полем `error`

### Requirement: Визуализация процесса обработки на клиенте
Веб-страница SHALL отображать степпер этапов обработки: шаги
«Конвертация файлов» → «Поиск различий» → «Анализ через LLM» в один ряд,
видимые всегда (до запуска — неподсвеченные). Во время обработки клиент
MUST опрашивать `GET /api/jobs/<job_id>` до финального статуса: первый
запрос — немедленно после запуска, далее — с интервалом 1 секунда.
Текущий этап MUST выделяться как активный, пройденные этапы — как
завершённые; при успехе все этапы отмечаются завершёнными и степпер
остаётся на экране, при ошибке сбойный этап отмечается как ошибочный и
отображается сообщение об ошибке.

#### Scenario: Степпер до запуска сравнения
- **Дано** пользователь открыл страницу и ещё не нажимал «Начать сравнение»
- **Когда** страница отображается
- **То** виден степпер из трёх этапов в неподсвеченном (сером) состоянии

#### Scenario: Отображение этапов во время обработки
- **Дано** пользователь нажал «Начать сравнение» и задача запущена
- **Когда** задача находится на этапе поиска различий
- **То** этап «Конвертация файлов» отмечен завершённым (зелёный)
- **И** этап «Поиск различий» отмечен активным (жёлтый с пульсацией)
- **И** опрос статуса выполняется каждую 1 секунду после немедленного первого запроса

#### Scenario: Успешное завершение обработки
- **Дано** задача сравнения успешно завершена
- **Когда** клиент получает финальный статус
- **То** все этапы степпера отмечены завершёнными (зелёный), степпер остаётся на экране
- **И** отображается результат сравнения

#### Scenario: Завершение обработки с ошибкой
- **Дано** задача сравнения завершилась ошибкой на этапе анализа через LLM
- **Когда** клиент получает финальный статус
- **То** пройденные этапы отмечены завершёнными, сбойный этап — ошибочным (красный)
- **И** отображается сообщение об ошибке

### Requirement: Инфраструктурный эндпоинт проверки состояния
Система SHALL предоставлять эндпоинт `GET /health`, возвращающий код 200
и JSON `{"status": "ok"}`. Эндпоинт предназначен для проверок живости
(liveness) инфраструктурой и MUST NOT требовать параметров, загруженных
файлов или запущенных задач.

#### Scenario: Проверка состояния
- **Когда** клиент запрашивает `GET /health`
- **То** ответ имеет код 200 и JSON `{"status": "ok"}`

### Requirement: Тестовые хуки конфигурации
Система SHALL поддерживать необязательные конфигурации `JOBS_SYNCHRONOUS`
и `LLM_CHAT` как dev/test-хуки маршрута `POST /api/compare`:
`JOBS_SYNCHRONOUS=True` — пайплайн выполняется синхронно внутри запроса
(без потока), `LLM_CHAT` — подмена chat-модели LLM произвольным объектом
с методом `invoke`. По умолчанию (без хуков) обработка MUST выполняться
асинхронно с chat-моделью, созданной из настроек окружения.

#### Scenario: Синхронный режим для тестов
- **Дано** в конфигурации приложения заданы `JOBS_SYNCHRONOUS=True` и подменённая chat-модель
- **Когда** клиент отправляет `POST /api/compare`
- **То** пайплайн сравнения завершается внутри запроса
- **И** опрос статуса сразу возвращает финальный статус задачи

### Requirement: In-memory хранилища задач и загрузок
Реестры загруженных файлов и задач сравнения SHALL храниться в памяти
процесса: данные MUST NOT переживать перезапуск приложения. После
перезапуска запрос с `upload_id` из прошлой сессии MUST отклоняться с
кодом 404 как запрос с неизвестным идентификатором.

#### Scenario: Идентификатор из прошлой сессии
- **Дано** файл был загружен до перезапуска приложения
- **Когда** клиент отправляет `POST /api/compare` с `upload_id` из прошлой сессии
- **То** ответ имеет код 404 и JSON с полем `error`

### Requirement: Класс изменения строки результата
В выровненных строках результата (`rows[]`) класс изменения стороны
MUST определяться так: для парных строк (обе стороны присутствуют) —
по метке классификации фрагмента (`changed`, `removed`, `added`); для
односторонних строк (противоположная сторона — пустое место) —
структурно, независимо от метки классификации: строка только со
стороной файла 1 MUST получать класс `removed`, строка только со
стороной файла 2 MUST получать класс `added`. Правило MUST применяться
и к односторонним строкам из чистых фрагментов `insert`/`delete`, и к
односторонним строкам «хвостов» replace-фрагментов разной длины.
Поведение MUST быть одинаковым при семантической классификации (LLM) и
при деградированной (по опкоду).

#### Scenario: Добавленный блок, классифицированный как changed
- **Дано** фрагмент `insert` (например, абзац только с картинкой) классифицирован как `changed`
- **Когда** формируются строки результата
- **То** сторона файла 2 получает класс `added`
- **И** пустое место в панели файла 1 отображается как место добавления (зелёный фон)

#### Scenario: Удалённый блок, классифицированный как changed
- **Дано** фрагмент `delete` классифицирован как `changed`
- **Когда** формируются строки результата
- **То** сторона файла 1 получает класс `removed`
- **И** пустое место в панели файла 2 отображается как место удаления (красный фон)

#### Scenario: Хвост replace-фрагмента разной длины
- **Дано** replace-фрагмент с двумя старыми и тремя новыми блоками, классифицированный как `changed`
- **Когда** формируются строки результата
- **То** парные строки получают классы по метке классификации
- **И** третья строка (только сторона файла 2) получает класс `added`

#### Scenario: Парные строки не затронуты
- **Дано** фрагмент `replace` из одной пары блоков, классифицированный как `changed`
- **Когда** формируются строки результата
- **То** обе стороны строки получают класс `changed` (пословная подсветка сохраняется)

### Requirement: Декомпозиция изображений блока в под-строки результата
Если у парных блоков (неизменённая строка либо изменённая пара) наборы
изображений различаются, строки результата (`rows[]`) MUST строиться
декомпозицией: текстовая часть блока образует парную строку без
изображений (пословный diff текста для изменённых пар сохраняется), а
изображения MUST выравниваться по подписям (sha1) в отдельные под-строки,
следующие за текстовой строкой. Под-строка изображений содержит только
изображения (без текста). Совпавшие по подписи изображения MUST образовать
парную под-строку без класса изменения; изображение только из файла 1
MUST образовать одностороннюю под-строку с классом `removed` и пустым
местом в панели файла 2; изображение только из файла 2 — одностороннюю
под-строку с классом `added` и пустым местом в панели файла 1; пара
изображений с разными подписями на парной позиции выравнивания MUST
образовать парную под-строку замены, обе стороны которой помечены
признаком различия изображений. Классы под-строк MUST быть структурными
и MUST NOT зависеть от метки классификации; поведение MUST быть
одинаковым при семантической классификации (LLM) и при деградированной.
Правило MUST NOT применяться к изображениям внутри таблиц и к
изображениям, отброшенным лимитом размера изображений.

#### Scenario: Картинка добавлена в абзац с неизменным текстом
- **Дано** в файле 2 в абзац добавлена картинка, текст абзаца не изменился
- **Когда** формируются строки результата
- **То** текст абзаца образует парную строку без подсветки
- **И** картинка образует одностороннюю под-строку с классом `added` (только сторона файла 2)

#### Scenario: Картинка удалена из абзаца с неизменным текстом
- **Дано** из файла 2 удалена картинка из абзаца, текст абзаца не изменился
- **Когда** формируются строки результата
- **То** текст абзаца образует парную строку без подсветки
- **И** картинка образует одностороннюю под-строку с классом `removed` (только сторона файла 1)

#### Scenario: Замена картинки при неизменном тексте
- **Дано** в одинаковом по тексту абзаце картинка файла 1 заменена другой картинкой в файле 2
- **Когда** формируются строки результата
- **То** картинки образуют парную под-строку замены
- **И** обе стороны под-строки помечены признаком различия изображений

#### Scenario: Неизменные картинки не декомпозируются лишний раз
- **Дано** оба документа содержат одинаковые картинки в одинаковых абзацах
- **Когда** формируются строки результата
- **То** картинки остаются в парных строках без класса изменения и без признака различия изображений

#### Scenario: Одинаково в обоих режимах классификации
- **Дано** абзац с различающимся набором картинок
- **Когда** формируются строки результата при семантической классификации и при деградированной
- **То** декомпозиция и классы под-строк одинаковы в обоих режимах

### Requirement: Парная конвертация PDF
Пайплайн сравнения двух PDF-файлов SHALL выполнять конвертацию парной
функцией, принимающей оба пути: выбор страниц для чтения, выравнивание
страниц и кропы требуют обоих документов. Сравнение файлов других
форматов SHALL выполняться пофайловой конвертацией без изменений.
Результат парной конвертации MUST включать блоки обеих сторон,
выравнивание страниц, кропы и признак усечения кропов.

#### Scenario: Два PDF конвертируются совместно
- **Дано** сравниваются два сканированных PDF
- **Когда** выполняется конвертация
- **То** конвертация выполнена одной функцией, получившей оба пути
- **И** результат содержит блоки обеих сторон и выравнивание страниц

#### Scenario: Сравнение .docx не меняется
- **Дано** сравниваются два файла `.docx`
- **Когда** выполняется конвертация
- **То** каждая сторона конвертируется пофайловой функцией
- **И** модель для чтения страниц не используется

#### Scenario: Признак усечения кропов в результате
- **Дано** кропы превысили настроенный лимит
- **Когда** формируется результат задачи
- **То** результат содержит признак усечения кропов

### Requirement: Передача модели в конвертацию
Пайплайн сравнения SHALL передавать модель в конвертацию документов
явным аргументом. Конвертация файлов, не требующих чтения страниц моделью,
MUST игнорировать переданную модель. Способ получения модели MUST позволять
подмену её тестовым моком без обращения к сети.

#### Scenario: Сканы читаются переданной моделью
- **Дано** сравниваются два сканированных PDF
- **Когда** выполняется конвертация
- **То** чтение страниц выполняется переданной моделью

#### Scenario: Конвертация .docx игнорирует модель
- **Дано** сравниваются два файла `.docx`
- **Когда** выполняется конвертация
- **То** модель не вызывается

#### Scenario: Подмена модели в тестах
- **Дано** в конфигурации задана тестовая модель
- **Когда** выполняется сравнение сканированных документов
- **То** чтение страниц выполняется тестовой моделью без обращения к сети

### Requirement: Выравнивание страниц в результате задачи
Результат завершённой задачи сравнения для PDF-документов MUST содержать
выравнивание страниц двух документов: список изменённых пар страниц, список
страниц только первого файла и список страниц только второго файла. Строки
результата MUST содержать номер страницы своей стороны. Результат MUST
содержать признак наличия визуальных различий между документами и признак
деградации, если чтение части страниц завершилось неудачей.

#### Scenario: Результат со сканированными документами
- **Дано** задача сравнения двух сканированных PDF успешно завершена
- **Когда** клиент запрашивает результат
- **То** результат содержит выравнивание страниц с номерами страниц обеих сторон
- **И** строки результата содержат номера страниц своих сторон

#### Scenario: Выравнивание со вставленной страницей
- **Дано** в файл 2 в середину документа вставлена страница
- **Когда** клиент запрашивает результат
- **То** выравнивание содержит страницу, присутствующую только в файле 2
- **И** прочие страницы сопоставлены по содержимому

#### Scenario: Результат с деградированным чтением
- **Дано** часть страниц не удалось прочитать моделью
- **Когда** клиент запрашивает результат
- **То** результат содержит признак деградации

### Requirement: Признак полного совпадения документов
Результат завершённой задачи сравнения PDF-документов MUST содержать признак
полного совпадения документов. Признак MUST быть истинным только тогда, когда
различий нет ни по тексту, ни по изображению и ни одна страница не осталась
непрочитанной или деградировавшей. Различие, обнаруженное только по изображению
при совпавшем тексте, MUST считаться различием, а не совпадением. Для сравнения
документов, не являющихся PDF, признак MUST отсутствовать. Решение о показе
сообщения о полном совпадении MUST приниматься по этому признаку, а не по
составу страниц результата: отсутствие неизменённых страниц само по себе
MUST NOT считаться признаком совпадения.

#### Scenario: Полностью совпадающие документы
- **Дано** задача сравнения двух PDF, у которых совпадает всё содержимое
- **Когда** клиент запрашивает результат
- **То** результат содержит признак полного совпадения со значением «истина»

#### Scenario: Различающиеся документы
- **Дано** задача сравнения двух PDF, у которых различается текст страниц
- **Когда** клиент запрашивает результат
- **То** результат содержит признак полного совпадения со значением «ложь»
- **И** результат содержит строки найденных различий

#### Scenario: Различие только по изображению
- **Дано** задача сравнения двух PDF, у которых текст всех страниц совпадает,
  но на одной странице заменено изображение
- **Когда** клиент запрашивает результат
- **То** результат содержит признак полного совпадения со значением «ложь»

#### Scenario: Деградировавшее чтение страниц
- **Дано** задача сравнения двух PDF, часть страниц которых не удалось прочитать
- **Когда** клиент запрашивает результат
- **То** результат содержит признак полного совпадения со значением «ложь»

#### Scenario: Сравнение документов не-PDF
- **Дано** задача сравнения двух файлов `.docx`
- **Когда** клиент запрашивает результат
- **То** результат не содержит признака полного совпадения

### Requirement: Прогресс конвертации многостраничных документов
Ответ `GET /api/jobs/<job_id>` MAY содержать необязательное поле прогресса
конвертации с указанием количества обработанных страниц и их общего числа.
Наличие прогресса MUST NOT изменять значения существующих полей ответа,
ключи этапов MUST оставаться прежними. Для документов, не требующих
постраничной обработки, поле прогресса MAY отсутствовать.

#### Scenario: Прогресс при чтении страниц
- **Дано** задача конвертирует сканированный PDF и обработала 12 страниц из 45
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ содержит прогресс «12 из 45»
- **И** ключ этапа остаётся прежним

#### Scenario: Отсутствие прогресса у документа .docx
- **Дано** задача сравнивает два файла `.docx`
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ не содержит поля прогресса

### Requirement: Ограничение объёма кропов в результате
Суммарный объём изображений визуально изменённых областей, передаваемых в
результате задачи, MUST ограничиваться настраиваемым лимитом на документ.
Превышение лимита MUST приводить к отбрасыванию части кропов и к установке
признака усечения кропов в результате. Ограничение кропов MUST NOT влиять на
текст блоков, на вычисление различий и на классификацию фрагментов.

#### Scenario: Кропы укладываются в лимит
- **Дано** суммарный объём кропов документа не превышает настроенный лимит
- **Когда** формируется результат задачи
- **То** все кропы переданы в результате
- **И** признак усечения кропов не установлен

#### Scenario: Кропы превышают лимит
- **Дано** суммарный объём кропов документа превышает настроенный лимит
- **Когда** формируется результат задачи
- **То** часть кропов отброшена, а результат содержит признак усечения кропов
- **И** строки результата и их классы изменений не изменились
