## Context

Текущий конвейер сравнения (`app/services/jobs.py`, `run_pipeline`):
конвертация → `normalize_blocks` → `find_diffs` → `refine_fragments` →
`classify_fragments` (LLM) → `_build_rows`.

`normalize_blocks` в `app/services/diffing.py` общая для `.docx` и `.pdf`:
схлопывает пробелы, хранит `\n`, отбрасывает пустые блоки, сохраняет `cells` и
изображения. Правила оформления (пункты 1, 2, 5, 6 из proposal) и снятие
маркеров списков (пункт 3) — PDF-специфичны и НЕ должны затрагивать `.docx`.

`refine_fragments` уже выделяет похожие replace-пары (ratio >= 0.6) и
направляет все фрагменты на `classify_fragments`, который возвращает только
`changed` / `removed` / `added`. Нет категории «оформление, не изменение».

Порядок операций (решение пользователя): PDF-нормализация **после** диффа
— фильтрация уточнённых фрагментов, а не нормализация входных блоков.

## Goals / Non-Goals

**Goals:**
- Фрагменты PDF, попадающие под правила оформления (5 пунктов), не
  подсвечиваются как изменения.
- Replace-фрагменты с похожими блоками направляются на VLM для вердикта
  «содержание vs оформление».
- Новая метка LLM `"formatting"`; при недоступности VLM — деградация на
  текущее поведение (`replace → changed`).
- `.docx` не затрагивается.

**Non-Goals:**
- Нормализация входных блоков до диффа (вне области по решению пользователя).
- Изменение `normalize_blocks` для `.docx`.
- Поддержка `.xlsx` (планируется отдельно).

## Decisions

### D1: Фильтрация после диффа, а не нормализация блоков
**Решение:** Вставить фильтрацию уточнённых фрагментов между
`refine_fragments` и `classify_fragments` (или внутри `_build_rows`) только
для пар PDF-блоков.
**Обоснование:** Пользователь явно выбрал порядок «нормализация после диффа».
Это не меняет входные тексты блоков (сохраняет оригинал для отображения) и не
троит `normalize_blocks` — общую для `.docx`.
**Альтернатива (отклонена):** Нормализация в `normalize_blocks` до диффа —
была бы проще, но изменила бы текст блоков для обеих сторон и затрагивала бы
`.docx` без параметра/флага.

### D2: Место реализации фильтра — `app/services/jobs.py` (`_build_rows`)
**Решение:** Фильтрация оформительных фрагментов выполняется в `_build_rows`
при построении строк результата: фрагменты с меткой `formatting` или
попадающие под правила 1, 2, 5, 6 пропускаются (не эмитится как различающиеся
строки).
**Обоснование:** `_build_rows` уже знает о фрагментах и метках; фильтрация там
минимально инвазивна и не меняет контракт `refine_fragments`.

### D3: VLM-проход для похожих replace-фрагментов
**Решение:** Для replace-фрагментов, где `refine_fragments` нашёл похожую пару
(ratio >= `SIMILARITY_THRESHOLD = 0.6`), система направляет фрагмент на VLM
через `classify_fragments` с расширенным набором меток.
Если возвращается `"formatting"` — фрагмент не подсвечивается.
**Обоснование:** Соответствует пункту 4 proposal и лучшим практикам
(Google Docs suggesting mode: algoritmo находит кандидата, VLM выносит
вердикт «редактирование контента» vs «только оформление»).
**Альтернатива (отклонена):** Жёсткий порог ratio (например, > 0.9) без VLM —
менее точно, не соответствует требованию «передавать фрагмент на анализ в VLM».

### D4: Четвёртая метка LLM `"formatting"`
**Решение:** Расширить `VALID_LABELS` в `app/services/llm.py` значением
`"formatting"` и обновить системный промпт: модель должна различать
содержательное изменение и только оформление.
**Обоснование:** Нужна явно 명시мая категория «не изменение», которую
клиент может отличить от `changed` и не подсвечивать.

### D5: Ограничение только на `.pdf`
**Решение:** Все PDF-специфичные правила применяются только когда оба файла
— `.pdf` (признак `is_pdf` в конверсии). `.docx` проходит старый путь без
изменений.
**Обоснование:** Пользователь подтвердил A: поведение наблюдалось только для
`.pdf`.

### D6: Порог сходства для VLM-прохода
**Решение:** Повторно использовать `SIMILARITY_THRESHOLD = 0.6` из
`refine_fragments` — те пары, которые уже считаются похожими, идут на VLM.
**Обоснование:** Порог уже измерен и зафиксирован в REVIEW.md; вводить новый
порог без данных не нужно.

## Risks / Trade-offs

| Риск | Митигация |
|------|-----------|
| Оформительный фрагмент пропущен фильтром и ушёл на VLM как `changed` — ложное срабатывание остаётся | VLM-вердикт `formatting` перекрывает; тесты на фикстурах |
| VLM недоступен для похожего replace-фрагмента — деградация на `changed`, фрагмент подсветится как изменение (ложное срабатывание) | Документировано как приемлемая деградация (как текущее поведение при недоступности LLM) |
| Изменение текста блока не предусмотрено (нормализация после диффа) — оригинал отображается как есть | Сохраняет инвариант `html` ↔ `text`; нет необходимости править отображение |
| Порог `0.6` может пропустить похожие блоки с ratio < 0.6 — они уйдут как delete+insert, не на VLM | Порог уже валидирован на регрессиях; можно ужесточить отдельным change |
| Маркеры списков снимаются на уровне текста блока, но HTML-представление может сохранять старый маркер | Необходимо обеспечить унификацию маркера при отображении (клиент или `_row_side`) |

## Migration Plan

- Архивация change: версия проекта `VERSION` повышается major `4.0.2 → 5.0.0`
  (уровень: несовместимое поведение).
- Откат: изменения только в логике фильтрации и метках LLM; можно откатить
  код до состояния до change, spec-артефакты остаются в `openspec/changes/`.
- Миграция данных не требуется (in-memory хранилища задач, нет persistent
  состояния различий).
