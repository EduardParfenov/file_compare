# Proposal: fix-one-sided-row-classification

## Why

Если во втором файле вставлен абзац только с картинкой (без текста), LLM
получает фрагмент «(пусто) vs (пусто)» и классифицирует его как
`changed` вместо структурно верного `added`. В результате блок в панели
файла 2 получает класс `changed` (зелёный фон — случайно совпадает с
правильным), а пустое место в панели файла 1 не получает класса вовсе и
остаётся серым: место вставки визуально не подсвечено, хотя по спеке
diff-viewer пустое место напротив добавленного блока должно быть
зелёным. Зеркальный случай (удаление, классифицированное как `changed`)
даёт серую заглушку вместо красной в панели файла 2. В деградированном
режиме (классификация по опкоду) дефект не проявляется — поведение
semantic/degraded режимов различается.

## What Changes

- Класс изменения односторонней строки результата (вторая сторона —
  `None`) определяется структурно, независимо от метки классификации:
  строка только с левой стороной — `removed`, только с правой —
  `added`. Метка LLM/классификатора применяется только к парным строкам.
- Покрываются оба источника односторонних строк: чистые фрагменты
  `insert`/`delete` и «хвосты» replace-фрагментов разной длины.
- Поведение semantic и degraded режимов уравнивается.

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `comparison-jobs`: добавляется требование о классе изменения строк
  результата: парные строки — по метке классификации, односторонние —
  структурно (`removed`/`added`) независимо от метки.

уровень: исправление

## Impact

- **Код**: `app/services/jobs.py` (`_side_change`/`_build_rows`),
  `tests/test_jobs.py` (новые тесты: insert/delete, классифицированные
  как `changed`; хвосты replace-фрагментов).
- **API**: в `rows[]` односторонние строки получают `removed`/`added`
  вместо `changed`; клиент без изменений (placeholder уже умеет
  `placeholder-added`/`placeholder-removed`).
- **Зависимости**: нет.
