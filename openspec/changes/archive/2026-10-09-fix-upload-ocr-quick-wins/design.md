## Context

Мотивация и состав изменений — в `proposal.md`. Текущее состояние трёх точек
правки (по состоянию кодовой базы на момент планирования):

- `app/services/uploads.py:22-23` — `secure_filename` применяется до
  `splitext`; для `документ.docx` Werkzeug вырождает имя в `docx`,
  расширение становится пустым, файл отклоняется. Имя в ответе — тоже
  вырожденное.
- `app/services/vision_ocr.py:171-175` — `store_result` вызывается
  безусловно, в том числе для `unreadable=True`: таймаут кладётся в кэш
  навсегда (до рестарта процесса).
- `app/services/uploads.py:10` и `app/services/jobs.py:30` — реестры
  `_UPLOADS` и `_JOBS` это голые `dict` без синхронизации; запись идёт из
  потока запроса (upload, create_job) и из фонового потока пайплайна
  (`run_pipeline` пишет `result`/`status`), чтение — из потоков запросов.
  `vision_ocr._CACHE` уже имеет `threading.Lock`.

Ограничения: развёртывание — вариант A (один процесс), поэтому Redis/
PostgreSQL не вводятся; правки не должны менять HTTP API и фронтенд.

## Goals / Non-Goals

**Goals:**

- Приём файлов с не-ASCII-именами при допустимом расширении (F1).
- Отсутствие перманентной деградации OCR после transient-сбоя (F3).
- Гарантированное отсутствие гонок на уровне записей реестров
  `_UPLOADS` / `_JOBS` при конкурентных запросах.

**Non-Goals:**

- TTL/эвикция реестров и вытеснение кэша страниц (отдельный пункт
  бэклога «Границы жизни состояния»).
- Магические байты, rate limiting, Docker/WSGI, дотяжка OCR/PDF-конфига
  (F2) — другие пункты бэклога.
- Защита от гонок на уровне **полей внутри** записи задачи (каждая
  отдельная запись атомарна под GIL; полная синхронизация состояния
  задачи — не часть этой правки).

## Decisions

### D1. Расширение — из оригинального имени, на диск — uuid + расширение

`ext = os.path.splitext(file_storage.filename or "")[1].lower()`, проверка
по `ALLOWED_EXTENSIONS`; имя на диске — как и сейчас, `upload_id + ext`
(`uuid4().hex` + валидированное расширение). `secure_filename` для имени
на диске не нужен — оно и так безопасно. Имя файла в ответе — исходное
имя клиента (спека требует «исходное имя файла»; фронтенд выводит его
через `textContent`, `app/static/app.js:58`, поэтому спецсимволы в имени
не опасны).

Альтернативы:

- *Санитизировать имя, сохраняя расширение* (`шляпа → shlyapa`) —
  избыточно: имя в ответе нигде не используется как путь; локализация
  транслита произвольна.
- *Валидировать до `secure_filename`, но сохранять sanitized-имя* —
  меняет отображаемое имя без выгоды.

Расширение с «точкой» вида `.docx` не может содержать `/`: проверка по
allowlist отсекает любые экзотические имена вида `a.exe/../../x`.

### D2. Неудачные результаты не кэшируются (без negative cache)

В `read_page` при `failed=True` пропустить `store_result`; успешные
результаты кэшируются как раньше. Никаких новых структур и TTL.

Альтернатива — negative cache с коротким TTL: защищает от шторма
повторных запросов к уже упавшей модели, но требует таймеров/очереди
очистки и новых настроек; в варианте A (один процесс, один оператор)
стоимость не оправдана. При необходимости это надстраивается позже без
изменения спека («неудача не создаёт запись» остаётся истиной для
negative cache с истёкшим TTL).

### D3. `threading.Lock` на каждый реестр, публичный API не меняется

Модули `uploads` и `jobs` получают приватный `_LOCK = threading.Lock()`;
каждая операция с реестром (`save_upload`/`get_upload_path`,
`create_job`/`get_job`/`set_stage`/`set_progress`/`clear_progress` и
записи `status`/`result`/`error`/`path_for_side` в `run_pipeline`)
выполняется под `with _LOCK`. Лок на уровне модуля (один на реестр), не
на уровне объекта: реестр и так один. Публичные сигнатуры и возвращаемые
значения не меняются — тесты и вызывающий код не затрагиваются.

Альтернативы:

- *Один общий лок* — проще, но без нужды сериализует независимые операции.
- *`queue`/акторы, `RLock`* — избыточно: операции над dict короткие,
  вложенных захватов нет.
- *Внешнее хранилище* — вне области (вариант A, см. Non-Goals).

### D4. Объём тестов — по поведению, не по механизмам

- `tests/test_upload.py`: загрузка `документ.docx`/`Отчёт.pdf` → 200,
  расширение на диске корректно; `заметки.txt` → 400; имя в ответе —
  исходное.
- `tests/test_vision_ocr.py`: первый вызов падает (мок), кэш пуст,
  повторный вызов с успешным моком идёт в модель и возвращает текст;
  успешный результат по-прежнему кэшируется (существующие сценарии
  остаются зелёными).
- `tests/test_jobs.py`: конкурентные `create_job` из N потоков → все
  id созданы и доступны через `get_job`; конкурентные `save_upload`
  в `tests/test_upload.py` аналогично.

Тест гонки — детерминированная проверка «N потоков, все записи на месте»,
не stress-тест: под GIL он ловит грубые ошибки (несинхронизированная
запись при resize-подобных операциях) и проверяет, что лок не ломает
поведение.

## Risks / Trade-offs

- [После D2 при длительном простое модели каждое повторное сравнение
  платит попыткой чтения по каждой странице] → деградация видна в
  интерфейсе и журнале; READ_ATTEMPTS=2 ограничивает стоимость одной
  страницы; лучше вечной деградации «до рестарта».
- [После D1 в ответе появляются имена с любыми символами Unicode] →
  вывод через `textContent` (безопасно), на пути не используются;
  allowlist расширений не ослабляется.
- [Локи добавляют contention при большом числе конкурентных запросов] →
  критические секции — операции над dict (наносекунды); пайплайн
  сравнения под локом не находится.
- [Потокобезопасность полей внутри записи задачи не гарантирована
  формально] → отдельные присваивания атомарны под CPython GIL; полная
  синхронизация — при выводе реестров за пределы одного процесса (B1/B2).

## Migration Plan

Деплой — обычный релиз (patch): правки обратно совместимы, API и формат
ответов не меняются, миграция состояния не нужна (in-memory реестры и так
не переживают рестарт). Откат — предыдущий образ/версия.
