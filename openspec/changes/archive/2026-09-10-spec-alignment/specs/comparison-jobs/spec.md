# comparison-jobs Delta

## ADDED Requirements

### Requirement: Инфраструктурный эндпоинт проверки состояния
Система SHALL предоставлять эндпоинт `GET /health`, возвращающий код 200
и JSON `{"status": "ok"}`. Эндпоинт предназначен для проверок живости
(liveness) инфраструктурой и MUST NOT требовать параметров, загруженных
файлов или запущенных задач.

#### Scenario: Проверка состояния
- **Когда** клиент запрашивает `GET /health`
- **То** ответ имеет код 200 и JSON `{"status": "ok"}`

### Requirement: Тестовые хуки конфигурации
Система SHALL поддерживать необязательные конфигурации `JOBS_SYNCHRONOUS`
и `LLM_CHAT` как dev/test-хуки маршрута `POST /api/compare`:
`JOBS_SYNCHRONOUS=True` — пайплайн выполняется синхронно внутри запроса
(без потока), `LLM_CHAT` — подмена chat-модели LLM произвольным объектом
с методом `invoke`. По умолчанию (без хуков) обработка MUST выполняться
асинхронно с chat-моделью, созданной из настроек окружения.

#### Scenario: Синхронный режим для тестов
- **Дано** в конфигурации приложения заданы `JOBS_SYNCHRONOUS=True` и подменённая chat-модель
- **Когда** клиент отправляет `POST /api/compare`
- **То** пайплайн сравнения завершается внутри запроса
- **И** опрос статуса сразу возвращает финальный статус задачи

### Requirement: In-memory хранилища задач и загрузок
Реестры загруженных файлов и задач сравнения SHALL храниться в памяти
процесса: данные MUST NOT переживать перезапуск приложения. После
перезапуска запрос с `upload_id` из прошлой сессии MUST отклоняться с
кодом 404 как запрос с неизвестным идентификатором.

#### Scenario: Идентификатор из прошлой сессии
- **Дано** файл был загружен до перезапуска приложения
- **Когда** клиент отправляет `POST /api/compare` с `upload_id` из прошлой сессии
- **То** ответ имеет код 404 и JSON с полем `error`

## MODIFIED Requirements

### Requirement: Этапные статусы задачи
Задача сравнения SHALL проходить этапы «Конвертация файлов...» → «Поиск
различий...» → «Анализ через LLM...» и завершаться статусом «готово» либо
«ошибка». Система SHALL предоставлять эндпоинт `GET /api/jobs/<job_id>`,
возвращающий текущий статус задачи, ключ текущего этапа (`stage`:
`converting` / `diffing` / `llm`), сообщение текущего этапа, а при
завершении — результат сравнения (блоки обоих документов и классифицированные
различия) либо сообщение об ошибке. Результат завершённой задачи MUST
включать поле `fragments_count` — число различающихся фрагментов,
переданных на классификацию. Запрос несуществующей задачи MUST
возвращать код 404.

#### Scenario: Опрос задачи в процессе обработки
- **Дано** задача сравнения запущена и находится на этапе поиска различий
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ содержит статус «в обработке», ключ этапа `diffing` и сообщение «Поиск различий...»

#### Scenario: Получение завершённой задачи
- **Дано** задача сравнения успешно завершена
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ содержит статус «готово»
- **И** результат со структурой обоих документов и классами различий для каждого фрагмента
- **И** результат содержит поле `fragments_count` с числом различающихся фрагментов

#### Scenario: Задача завершилась ошибкой
- **Дано** задача сравнения завершилась ошибкой конвертации
- **Когда** клиент запрашивает `GET /api/jobs/<job_id>`
- **То** ответ содержит статус «ошибка» и сообщение об ошибке

#### Scenario: Запрос несуществующей задачи
- **Когда** клиент запрашивает `GET /api/jobs/<несуществующий_id>`
- **То** ответ имеет код 404 и JSON с полем `error`
