# Design: highlight-opposite-word-marks

## Context

См. proposal.md — Why. `inline_diff` (app/services/diffing.py) возвращает
для изменённой пары блоков сегменты `{"text", "type"}` каждой стороны;
типы: `same`, `add`, `del`, `chg`. На чистых opcode'ах `delete` сегмент
`del` эмитится только слева, на `insert` — `add` только справа.
Фронтенд `appendSegments` (app/static/app.js) рендерит `same` как текст,
остальные типы — как `<span class="seg-<type>">`; пустой `textContent`
допустим. Фоновые цвета уже в git-стиле (change
`align-block-heights-git-colors`).

## Goals / Non-Goals

**Goals:**
- Видимая метка места изменения в противоположной панели для чистых
  удалений/добавлений слов, без искажения текста документа.
- Цвета меток по git-схеме: красная напротив удалённого, зелёная
  напротив добавленного.

**Non-Goals:**
- Маркеры внутри `replace`-фрагментов пословного diff (замена слова) —
  там обе стороны уже подсвечены, метка была бы шумом.
- Изменение фронтенд-рендеринга сегментов — существующий код уже
  обрабатывает произвольные типы.
- Метки для блоковых удалений/добавлений — уже решено цветными
  заглушками в `align-block-heights-git-colors`.

## Decisions

### D1: Пустые маркерные сегменты на чистых delete/insert opcode'ах

В `inline_diff`: на opcode `delete` в правый список добавляется
`{"text": "", "type": "del-mark"}`; на opcode `insert` в левый —
`{"text": "", "type": "add-mark"}`. Маркер ставится в позицию,
соответствующую месту разрыва (между окружающими `same`-сегментами).
`_append_segment` пропускает пустой текст и сливает соседние типы —
для маркеров он не используется, сегменты добавляются напрямую.
Пустой текст сохраняет инвариант «конкатенация сегментов == текст
стороны» (есть тест).

Альтернативы:
- Маркер с текстом-заполнителем (например `&nbsp;`) — искажает
  инвариант конкатенации и копирование текста из панели.
- Подсветка соседнего слова/пробела — визуально неоднозначно,
  пользователь выбрал узкую метку-полосу.

### D2: Маркеры только на чистых delete/insert, не внутри replace

Внутри `replace`-фрагмента (замена слова) непарные токены получают
`del` слева и `add` справа — обе стороны подсвечены в одном месте,
место изменения очевидно. Добавление туда маркеров создало бы
визуальный шум без новой информации.

### D3: Отображение метки как узкой полосы через CSS

`.seg-del-mark`, `.seg-add-mark`: `display: inline-block`,
`width: 3px`, `height: 1em`, `vertical-align: text-bottom`, фон
`var(--red-light)` с нижней границей `#e53935` / `var(--green-light)`
с границей `var(--green)` — стиль согласован с существующими `seg-del`/
`seg-add` (фон + нижняя граница). Пустой span получает видимые размеры
только за счёт CSS, текст панели не меняется.

## Risks / Trade-offs

- [Полоса 3px может быть незаметна при беглом просмотре] → Полоса
  цветная с границей, как у словесной подсветки; при необходимости
  ширину легко увеличить (одна константа в CSS).
- [Маркер между `same`-сегментами может попасть в середину пробела] →
  Приемлемо: метка показывает точку разрыва, точность до токена
  сохраняется (SequenceMatcher ставит разрыв на границе токенов).
- [Существующие тесты фиксируют отсутствие маркеров] → Осознанное
  изменение контракта: два теста `test_diffing.py` обновляются,
  добавляются тесты на наличие и позицию маркеров.
