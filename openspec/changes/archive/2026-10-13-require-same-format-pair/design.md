## Context

Мотивация — в `proposal.md` (раздел Why). Здесь — только то, что влияет на
выбор способа.

Проверка расширения должна случиться там, где известны **оба** файла:
загрузка (`/api/upload`) пофайловая и о паре ничего не знает, а
`jobs.start_job` уже создаёт задачу и запускает поток — отклонить после
этого можно только как `failed`, а не как `400`. Единственная точка, где
оба идентификатора есть и задача ещё не создана, — роут
`POST /api/compare` (`routes.py:50`).

Расширение уже доступно без новых полей: `uploads._UPLOADS` хранит путь
вида `<upload_id><ext>`, причём `ext` записан через `.lower()`
(`uploads.py:30`). Клиенту сервер уже возвращает исходное имя файла
(`uploads.py:39`), из которого расширение извлекается на стороне браузера.

## Goals / Non-Goals

**Goals:**

- Смешанная пара не доходит до конвертации и возвращает `400` с внятным
  сообщением.
- Пользователь видит причину **до** нажатия кнопки, а не после провала
  задачи.
- README и текст страницы говорят об ограничении явно.
- Правило формулируется как «одинаковое расширение», чтобы при появлении
  `.xlsx` (заявлен в планах) оно заработало без правок.

**Non-Goals:**

- Проверка содержимого файла по magic bytes — отдельный пункт `BACKLOG.md`,
  не смешивается с этим change'ом.
- Автотесты клиентской части — в проекте нет jsdom/playwright (пункт
  бэклога); проверка кнопки остаётся ручным сценарием.
- Перенос правила на уровень сервиса `jobs` или `conversion`.
- Удаление ветки `ValueError` в `convert_document`: она остаётся защитой
  от некорректного прямого вызова сервиса и покрыта тестами уровня сервиса.

## Decisions

### D1. Проверка в роуте `/api/compare`, не в сервисе

`routes.py` сверяет расширения после успешного поиска обоих `upload_id` и
перед `jobs.create_job()`.

Альтернативы и почему нет:

- **В `jobs.start_job`** — задача уже создана, ответ придётся формировать
  как `failed` вместо `400`; плюс сервис станет знать про HTTP-коды.
- **В `convert_pair`** — слишком поздно: на этом этапе уже запущен поток
  пайплайна и выставлен статус `processing`.
- **В `uploads`** — неверный уровень: загрузка пофайловая, пары там нет.

### D2. Сравниваются расширения сохранённых путей, в нижнем регистре

Берётся `os.path.splitext(path)[1].lower()` для обоих путей из
`get_upload_path`. Источник — то, что реально пойдёт в конвертер, а не
исходное имя клиента: имя может содержать кириллицу и нестандартный
регистр, а сохранённое расширение уже нормализовано при загрузке.

Порядок проверок в роуте сохраняет текущие коды: отсутствие идентификатора
→ `400`, неизвестный идентификатор → `404`, различие расширений → `400` с
сообщением «Сравнивать можно только файлы одного формата».

### D3. Клиентское состояние — расширение, а не объект `File`

Рядом с `uploads = {1, 2}` вводится карта расширений, заполняемая в
`uploadFile` из `body.filename` (`.toLowerCase()`), и `updateCompareButton`
гасит кнопку при несовпадении; причина показывается через существующий
`showError`.

Альтернатива — хранить сам `File`: отвергнута, потому что объект после
загрузки серверу не нужен, а `filename` уже приходит в ответе — единый
источник имени и на сервере, и в браузере.

Ограничение: клиентская проверка — удобство, не гарантия. Гарантия —
серверная (`D1`); если она разойдётся с клиентской, страдает только
подсказка, а не результат.

### D4. Текст сообщений и документация

- Сервер: `400` + `{"error": "Сравнивать можно только файлы одного формата"}`.
- Клиент: та же формулировка через `showError`, чтобы пользователь не видел
  отдельной, отличающейся формулировки.
- `index.html`: «Загрузите две версии документа одного формата (`.docx`,
  `.pdf`)».
- `README.md`: явное ограничение в разделе «Как это работает».

## Risks / Trade-offs

- [Смешанные пары, работавшие раньше (`.docx` + PDF с текстовым слоем),
  теперь отклоняются] → осознанный breaking change: уровень
  «несовместимое поведение», major-версия, ограничение отражено в README и
  в спеке. Откат — снятие одной проверки в роуте.
- [Клиентская ветка не покрыта автотестами] → ручной сценарий в задачах
  change'я; системное закрытие — пункт бэклога «тесты для клиентской
  части», не этот change.
- [Правило завязано на расширение, а не на содержимое] → файл с ложным
  расширением пройдёт проверку пары так же, как сейчас проходит проверку
  загрузки; борьба с этим — magic bytes, отдельный пункт бэклога.
- [Клиент может разойтись с сервером (например, имя пришло без
  расширения)] → серверная проверка всегда авторитетна; при расхождении
  запрос всё равно будет корректно отклонён сервером.
