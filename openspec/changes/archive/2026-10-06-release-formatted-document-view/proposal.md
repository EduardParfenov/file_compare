# Proposal: release-formatted-document-view

## Why

Ветка `formatted-document-view` содержит четыре готовых коммита с крупной
функциональностью (форматированный вид документов, декомпозиция изображений,
структурный класс односторонних строк, горизонтальная прокрутка широких
таблиц; `VERSION` 0.1.1 → 1.0.3), но `master` отстаёт на эти четыре коммита —
функциональность не выпущена. Простое открытие PR невозможно завершить
слиянием: конвейер CI на этой ветке падает — `ruff format --check` на трёх
файлах и `ruff check` на двух находках (S112, UP031), то есть изменения из
четырёх коммитов попали в репозиторий без локального прогона закреплённых
проверок. Одновременно в проекте нет закреплённой процедуры выпуска: не
описано, что именно делает ветка готовой к слиянию (какой состав проверок),
в какую ветку вливается PR, каким способом выполняется слияние и создаются
ли теги — решение принимается каждый раз заново.

## What Changes

- **Правки стиля, без изменения поведения** (минимальный дифф, необходимый
  для зелёного CI):
  - `ruff format` по трём файлам: `app/services/docx_converter.py`,
    `app/services/jobs.py`, `tests/test_jobs.py`.
  - `S112` (`try-except-continue`) в `app/services/docx_converter.py:118` —
    подавление через расширенную существующую метку
    `# noqa: BLE001, S112`, по конвенции репозитория (логирование в `app/`
    не используется).
  - `UP031` (`%`-форматирование) в `tests/test_jobs.py:749` — переход на
    f-строку.
- **Новая спека `release-process`**: закреплённая процедура выпуска —
  критерий готовности ветки (локальный прогон `ruff format --check .`,
  `ruff check .`, `pytest`, `openspec validate --all --strict` до push),
  цель PR — `master`, требование зелёных проверок перед слиянием, merge-коммит
  как способ слияния (не squash, не rebase), отсутствие тегов и GitHub
  Release, удаление remote-ветки после слияния.
- **Дополнение спеки `continuous-integration`**: требование о блокирующем
  статусе проверок — PR в `master` вливается только при успешном прохождении
  всех шагов CI, а локальный прогон тех же команд с закреплёнными версиями
  (`requirements-dev.txt`) обязателен до push, поскольку расхождение
  локального и раннерного окружения проявляется уже на CI.
- **Архивация change'а до открытия PR** с bump `VERSION` patch
  (1.0.3 → 1.0.4) — по правилу `openspec/config.yaml`, версия повышается при
  архивации, а не при слиянии; архив и версия попадают в тот же PR.
- **Выпуск ветки**: PR `formatted-document-view` → `master` с описанием
  четырёх коммитов и состава проверок; слияние merge-коммитом (как в PR #2);
  теги и GitHub Release не создаются; после слияния remote-ветка удаляется.

уровень: исправление

## Capabilities

### New Capabilities

- `release-process`: процедура выпуска ветки в `master` — критерий готовности
  ветки к PR, цель и содержание PR, блокирующие проверки, способ слияния
  (merge-коммит), отсутствие тегов и удаление ветки после слияния.

### Modified Capabilities

- `continuous-integration`: добавляется требование о блокирующем статусе
  проверок — слияние PR в `master` только при зелёном CI и обязательный
  локальный прогон закреплённых команд проверки до push.

## Impact

- **Код**: правки только стилевые — `app/services/docx_converter.py`
  (форматирование вызова `images.append`, метка `noqa`), `app/services/jobs.py`
  (форматирование `rows.append`), `tests/test_jobs.py` (форматирование,
  f-строка вместо `%`). Логика конвертера, сборки строк результата и тестов не
  меняется; `pytest` — 118 passed до и после.
- **Поведение приложения, API, payload**: не меняется. Контракт `rows[]`,
  блоки `{text, html, images}`, HTTP-эндпоинты и требования
  `comparison-jobs`, `diff-viewer`, `document-diff`, `file-upload`,
  `llm-classification`, `markdown-conversion` не затрагиваются — спеки для
  них дельт не имеют.
- **Git/GitHub**: один PR `formatted-document-view` → `master`; merge-коммит;
  теги и Release не создаются; ветка `formatted-document-view` удаляется на
  remote после слияния. Конвейер CI не меняется (`.github/workflows/ci.yml`
  уже триггерится на `pull_request`), триггер `push: branches: [master]`
  остаётся в силе.
- **Версия**: patch (1.0.3 → 1.0.4) при архивации этого change'а.
- **Зависимости**: не меняются (`requirements.txt`,
  `requirements-dev.txt` не входят в дифф ветки), поэтому `pip-audit` и
  `gitleaks` не получают новых входных данных; риск для них — только
  содержимое новых файлов (`.env.example` получает две строки-комментария
  без секретов).
- **Не входит в объём**: переименование `master` в `main` и изменение
  триггеров CI; branch protection и обязательные статусы на стороне GitHub
  (в репозитории не настроены, требование закрепляется как процедура, а не
  как настройка); теги, GitHub Release, CHANGELOG; исправление замечаний
  `BACKLOG.md`/`REVIEW-CRITICAL.md` (in-memory хранилища, magic bytes, rate
  limiting, тесты клиентской части).
