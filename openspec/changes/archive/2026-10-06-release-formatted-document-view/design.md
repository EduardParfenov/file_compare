## Context

См. proposal.md — Why. Технические вводные, определившие подход:

- `master` — дефолтная ветка `EduardParfenov/file_compare`; ветки `main` в
  репозитории нет, CI триггерится на `push` в `master` и на `pull_request`.
- `formatted-document-view` опережает `origin/master` ровно на 4 коммита,
  отставания нет, рабочее дерево чистое, ветка полностью запушена. Дифф —
  42 файла, из них кода 4 (`docx_converter.py`, `jobs.py`, `tests/test_jobs.py`,
  `tests/test_docx_converter.py`), остальное — спеки, архивы change'ей,
  фронтенд, README/REVIEW, `.env.example`.
- Локальный прогон закреплённых инструментов (`ruff==0.16.7` из
  `requirements-dev.txt`, конфигурации ruff в репозитории нет) даёт:
  `pytest` — 118 passed, `openspec validate --all --strict` — 8 passed /
  0 failed, `ruff format --check .` — 3 файла, `ruff check .` — 2 находки
  (S112, UP031). Расхождение воспроизводится с `--isolated`, то есть это не
  влияние локального окружения, а состояние кода ветки.
- Находки локализованы: `S112` — один `except Exception: continue` в
  `_paragraph_images`, `UP031` — одно `%`-форматирование в
  `tests/test_jobs.py`. Обе находки не меняют поведение.
- В `app/` нет ни одного использования `logging`; подавление `except`
  оформлено инлайн-метками `# noqa: BLE001 — <причина>` (3 места).
- Предыдущий PR #2 слит merge-коммитом (два родителя, коммиты ветки
  сохранены). Тегов в репозитории нет.
- Проектный порядок выпуска: версия повышается при архивации change'а
  (`openspec/config.yaml`), каждый завершённый change архивируется в том же
  коммите, что и его изменения (см. четыре коммита ветки).

## Goals / Non-Goals

**Goals:**

- Получить один PR `formatted-document-view` → `master` с зелёным CI и
  слить его merge-коммитом, сохранив четыре исходных коммита.
- Устранить расхождение с CI минимальным диффом без изменения поведения.
- Закрепить повторяемую процедуру выпуска в спеке, а не в переписке.

**Non-Goals:**

- Не менять функциональность приложения, контракты API/payload и спеки
  `comparison-jobs`, `diff-viewer`, `document-diff`, `file-upload`,
  `llm-classification`, `markdown-conversion`.
- Не переименовывать `master` в `main`, не создавать ветку `main`.
- Не добавлять branch protection, обязательные статусы, теги, Release,
  CHANGELOG и не трогать `BACKLOG.md`/`REVIEW-CRITICAL.md`.

## Decisions

**Правки стиля — автоматическим `ruff format`, а не вручную.**
Форматирование применяется один раз инструментом той же версии, что и в CI,
поэтому повторный локальный прогон даёт нулевой дифф и расхождение
воспроизводимо. Альтернатива (править три места руками) отклонена: ручная
правка форматтера расходится с ним при следующем прогоне.

**`S112` — расширить существующую метку `noqa`, а не вводить логирование.**
Поведение «битое изображение не отменяет конвертацию» намеренное и уже
зафиксировано комментарием; `logging` в `app/` не используется, и его
введение ради одной находки — это отдельное архитектурное изменение
(уровень конфигурации, формат вывода, sink), выходящее за рамки выпуска.
Альтернатива `try/except/else` или сужение `except` не подходит: `part.blob`
и `related_parts` могут отдать любой объект с ошибкой произвольного типа,
перехват `Exception` здесь — осознанный. Итоговая метка:
`# noqa: BLE001, S112 — битое изображение не отменяет конвертацию`.

**`UP031` — f-строка.** Правка в тестовом хелпере на одну строку; другие
варианты (`format()`, конкатенация) стилистически хуже и не соответствуют
соседнему коду.

**Архив change'а и bump `VERSION` — в ветке до создания PR.**
Правило проекта повышает версию при архивации. Если архивировать после
слияния, bump версии придётся отдельным коммитом прямо в `master` — то есть
`master` получит изменение вне PR и вне проверок. Архивация до PR делает
ветку самодостаточной: функциональность, спеки, архив и версия (1.0.3 →
1.0.4) приезжают одним слиянием. Альтернатива «отдельный PR на версию»
отклонена: ради patch-бампа поднимать второй PR несоразмерно.

**Правки стиля — отдельным коммитом от четырёх feature-коммитов.**
История ветки остаётся читаемой: коммит `fix: форматирование и линтер перед
выпуском` не смешивается с изменениями поведения. В PR он попадает так же,
как остальные, — merge-коммит этого не скрывает.

**PR открывается после локального зелёного прогона, а не «открыть и
смотреть».** Три дополнительных прогона (`ruff format --check .`,
`ruff check .`, `openspec validate --all --strict`) дешевле, чем цикл
коммитов «fix → push → ждать CI → снова fix», и соответствует требованию
«критерий готовности ветки».

**Слияние — merge-коммитом.** Совпадает с прецедентом PR #2 и сохраняет
четыре коммита с архивами; squash сделал бы историю выпуска невоспроизводимой
(см. требование `release-process`).

**Теги и Release не создаются.** Решение владельца; версия распространяется
файлом `VERSION`, дополнительного канала распространения у проекта нет.

**Задание PR берётся с удалённого состояния ветки.** Перед созданием PR
выполняется `git fetch` и сверка `origin/master...origin/formatted-document-view`,
чтобы «опережает на 4 / отстаёт 0» было фактом на момент открытия PR, а не
состоянием начала сессии.

## Risks / Trade-offs

- **[Правка форматирования задевает строки, отвечающие за diff-строки]**
  `jobs.py:205` — это `rows.append` для односторонней вставки изображения.
  Форматирование меняет только раскладку, но рядом стоит нетривиальная логика
  (`replace`-пары, хвосты) → переформатирование может скрыть реальную ошибку
  → митигация: `pytest` до и после (118 passed) и просмотр диффа
  `git diff -w` (показывает только смысловые изменения).
- **[Раннер может упасть на шагах, которые локально не проверяются]**
  `gitleaks` (fetch-depth 0) и `pip-audit` локально не гоняются. Зависимости
  в диффе ветки не менялись, новые файлы — `.env.example` с комментариями и
  тексты спек → риск низкий → митигация: при красном шаге чинить в ветке
  отдельным коммитом, слияние не форсировать (требование «зелёный CI как
  условие слияния»).
- **[Архивация change'а до PR требует, чтобы apply был полностью завершён]**
  архив до зелёного прогона оставил бы в `master` архив незавершённой работы
  → митигация: порядок «правки → зелёный прогон → архив → повторный
  `openspec validate --all --strict` → push».
- **[Удаление remote-ветки необратима]** → митигация: выполняется отдельной
  последней командой после подтверждения merge-коммита в `master`; локальная
  копия ветки остаётся, все четыре коммита живут в истории `master`.
- **[Компромисс: требование о зелёном CI закреплено как процедура, а не как
  настройка]** branch protection в репозитории не настроен, и обойти проверки
  технически возможно → осознанно: настройка GitHub вынесена из объёма,
  спека фиксирует ожидаемое поведение процесса.
- **[Компромисс: patch-бамп до 1.0.4 для стилевых правок]** версия
  отражает завершённый выпуск, а не наличие стилевых изменений; bump
  обязателен по правилу проекта для каждого change'а.
