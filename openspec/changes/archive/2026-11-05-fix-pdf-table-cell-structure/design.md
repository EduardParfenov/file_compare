## Context

В текущем конвейере PDF с текстовым слоем (`pdf_converter.py`) строки таблиц
склеиваются из слов через `_merge_lines`, затем `_clean` схлопывает все
многократные пробелы в один. Функция `_table_row_text` делит склеенный текст
по `"  "` (двойному пробелу), но после `_clean` таких пробелов не остаётся.
В итоге вся строка таблицы становится одной ячейкой, поле `cells` не
создаётся, и фронтенд (`renderTableSide` в `app.js`) не распознаёт блок как
табличную строку — рендерит его как обычный абзац «сплошняком».

Фронтенд уже поддерживает `block.cells` и `block.cell_segments` (см.
`renderTableSide`, `weaveTableSegments`), и `_enrich_table_block` в `jobs.py`
уже парсит `cells` из текста — но только если текст содержит разделители `|`.
Для PDF эта цепочка разрывается на этапе конвертера.

## Goals / Non-Goals

**Goals:**
- Блок строки таблицы PDF содержит поле `cells: list[str]` с текстами ячеек
- `cells` сохраняется через нормализацию (`normalize_blocks`) без пере-parсинга
- `cells` пробрасывается в клиент через `_row_side`
- Фронтенд отрисовывает таблицу с правильными границами ячеек и выравниванием колонок
- Инвариант `textContent(html) == text` сохраняется

**Non-Goals:**
- Не изменять ветку чтения страниц моделью (сканы) — там таблицы уже приходят
  в markdown-формате `| a | b |` и работают через существующий путь
- Не определять объединённые ячейки (colspan/rowspan) в PDF таблицах
- Не менять контракт блока для не-PDF форматов (docx уже имеет cells через
  parse_table_row)

## Decisions

1. **Ячейки определяются по координатам слов (`x0`/`x1`), а не по split("  ")**
   - Альтернатива: оставить split("  ") и не схлопывать пробелы в `_clean`
   - Отклонено: `_clean` используется и для обычных абзацев, где многократные
     пробелы — шум. Схлопывание оставить, для таблиц брать координаты из
     `page.extract_words()`, которые уже доступны
   - Табличные строки выявляются через `page.find_tables()` (уже есть в коде)
   - Слова строки кластеризуются по горизонтальным позициям (`x0`/`x1`) —
     слова с близкими `x0` относятся к одной ячейке

2. **`build_block` для тега `tr` принимает опциональный `cells: list[str]`**
   - Альтернатива: добавлять `cells` уже после build_block, в `convert_pdf_text_layer`
   - Отклонено: единый пункт вставки в `build_block` гарантирует, что `cells`
     всегда présence в блоке таблицы, и html + cells согласованы

3. **`normalize_blocks` копирует `cells` без изменений, не пере-parсит**
   - Альтернатива: пере-parсить `cells` из `text` в нормализаторе
   - Отклонено: текст схлопывается (пробелы внутри ячеек могут измениться),
     `cells` должен хранить исходный текст ячеек как пришёл от конвертера

4. **`_enrich_table_block` не пере-parсит `cells`, если они уже есть**
   - Альтернатива: всегда пере-parсить из текста для единообразия
   - Отклонено: для PDF текст уже не содержит надёжных разделителей ячеек,
     пере-parсинг с destroying уже существующие корректные `cells`

## Risks / Trade-offs

[Кластеризация слов по `x0`/`x1` может ошибиться, если в PDF нет чётких зазоров между колонками] → Слова из соседних ячеек могут слиться; падение деградается до одной ячейки (как сейчас), что не хуже текущего поведения

[Объединённые ячейки (colspan/rowspan) не поддерживаются] → python-docx для .docx обрабатывает их, для PDF нет информации в текстовом слое; приемлемое ограничение, зафиксировано в Non-Goals

[Разное число колонок у двух файлов] → Фронтенд уже дополняет пустые `<td>`; без общей сетки ширина колонок между панелями может не совпадать — отдельная проблема фронтенда, не блокирует этот change

[Инвариант `textContent(html) == text` при наличии `cells`] → html строится из тех же ячеек, что и `cells`, инвариант сохраняется по построению
