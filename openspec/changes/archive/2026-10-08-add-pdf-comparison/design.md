## Context

Текущее состояние, важное для решения (мотивация — в `proposal.md`).

Контракт блока документа — `{text, html, images}`; он производный от
`.docx`-конвертера и переиспользуется всеми стадиями пайплайна. `html`
используется клиентом через `innerHTML`, а пословная подсветка вплетается в
DOM функцией `weaveSegments` при предусловии `div.textContent === block.text`
(`app/static/app.js:275`). При нарушении этого инварианта клиент молча
деградирует до plain text — потеря форматирования без ошибки.

Алгоритмический diff (`app/services/diffing.py`) работает с плоской
последовательностью блоков и ничего не знает о страницах. Страж
`MAX_REFINE_PAIRS = 2500` (diffing.py:19) отключает уточнение replace-фрагментов
при превышении числа пар блоков, `MAX_INLINE_TOKENS = 2_000_000`
(diffing.py:22) отключает пословный diff внутри длинных блоков. Обе деградации
молчаливы: баннер «деградированный режим» в `app.js:454` отражает только
признак `semantic` от классификатора, а не деградацию diff.

`_build_rows` (`app/services/jobs.py:222`) превращает фрагмент в
`max(len(old), len(new))` строк. Результат задачи — единый список строк
`rows[]`; клиент группирует подряд идущие строки таблиц в одну HTML-таблицу и
выравнивает высоты парных блоков.

Изображения блоков передаются в JSON как data-URI, поэтому результат задачи уже
может быть крупным. `MAX_CONTENT_LENGTH` по умолчанию 16 МБ,
`MAX_IMAGES_TOTAL_BYTES` — 10 МБ (лимит изображений `.docx`).

Одна и та же модель (`LLM_MODEL`) обслуживает и классификацию фрагментов, и
чтение страниц — по разу это разные задачи с разными параметрами вызова, но по
конфигурации это один и тот же клиент. Клиент создаётся из ключей префикса
`LLM_` (`app/services/llm.py:34`), а таймаут захардкожен и общий для обоих
вызовов (`llm.py:23`). Мультимодальные content-блоки поддерживаются используемой
библиотекой без отдельного клиента.

## Goals / Non-Goals

**Goals:**

- Существующий пайплайн (diff, уточнение фрагментов, классификация, сборка
  строк, пословная подсветка) остаётся неизменным. PDF подключается как
  источник блоков, а не как новый вид сравнения.
- Изменения детектируются по содержимому, а не по номеру страницы: вставка
  листа не должна помечать остальные страницы.
- Стоимость обработки пропорциональна числу реально изменённых страниц, а не
  числу страниц документа.
- Ответ модели никогда не подставляется в DOM напрямую и не может нарушить
  инвариант `textContent === text`.
- Модель и её параметры настраиваются через окружение; ни одного
  внутреннего адреса и ни одной кодировки промпта в репозитории.

**Non-Goals:**

- Точная привязка кропа изменённой области к конкретной строке для
  сканированных документов (требует надёжных координат слов от модели).
- Просмотрщик PDF с наложением подсветки (pdf.js и аналоги) — отдельный
  продукт.
- Резервный детерминированный OCR (tesseract/paddle) как источник текста или
  как перекрёстная проверка модели.
- Формат `.xlsx`.
- Изменение алгоритма diff: сравнение блоков остаётся плоским.

## Decisions

### D1. Парная точка входа для PDF, пофайловая для остального

`convert_document(path)` работает с одним файлом и этого достаточно для
`.docx` и для ветки текстового слоя. Для скана недостаточно: решение «какую
страницу не читать» невозможно без второго документа. Поэтому рядом живёт
`convert_pdf_pair(path1, path2, vision_chat)`, которая рендерит обе книги,
сопоставляет страницы и только потом обращается к модели.

```
convert_document(path1)          convert_pdf_pair(path1, path2)
  └─ не знает про path2            ├─ align_pages -> что читать
  └─ читает всё                    ├─ read_pages  -> только изменённые
                                   └─ crops       -> визуальные правки
```

Альтернатива — считать выравнивание внутри пайплайна после пофайловой
конвертации. Отклонена: конвертация успела бы прочитать все страницы, то
есть экономия, ради которой затевался image-diff, пропала бы.

Следствие для отображения: совпавшие страницы не дают блоков, поэтому
показываются свёрнутыми диапазонами; изменённые страницы, наоборот,
показываются целиком — текст уже прочитан, прятать его незачем.

### D2. Три отдельных модуля, один контракт блока

`pdf_converter.py` (выбор ветки, сборка блоков), `vision_ocr.py` (запросы к
модели, кэш, деградация), `page_image_diff.py` (рендер, маска, выравнивание,
кропы). Разделение по причине отказа: у них разные зависимости (pdfplumber,
langchain, pypdfium2), разные политики отказа и разные точки мокирования в
тестах.

Альтернатива — один `pdf_converter.py` на 400+ строк. Отклонена: смешивает
вызов модели с пиксельной арифметикой, а тесты на деградацию модели требуют
подмены только одного слоя.

### D3. Страница — единица передачи модели, блок — единица сравнения

Это центральное решение. Одно изображение страницы на запрос. Ответ модели
разбирается на блоки: заголовки, абзацы, строки markdown-таблиц.

Почему не сравнивать по страницам: правка одного слова внутри абзаца дала бы
одну строку результата на страницу, и вся страница была бы помечена как
изменённая — подсветка расползлась бы на весь абзац вместо одного слова.

Почему не дробить на строки: OCR двух сканов нестабилен по границам строк
(кегль, выключка, ширина набора), поэтому построчный diff каскадирует —
изменение одной строки вызывает изменение всех последующих строк абзаца.
Именно поэтому отраслевые OCR-пайплайны (marker, docling, olmocr) отдают
markdown-блоки, а не строки.

Следствие, полезное само по себе: строка markdown-таблицы — это уже тот формат,
который понимает `parse_table_row` (diffing.py:36). Таблица из скана попадает в
существующий путь отображения таблиц и получает пословную подсветку по ячейкам
без нового кода на клиенте.

### D4. Правка генерируется кодом, а не моделью

Модель читает (страница → markdown). Сравнивает код. Вариант «две картинки →
список изменений» отклонён: он не даёт пословной подсветки (нужны обе версии
текста), недетерминирован, галлюцинирует правки, не отличает перенос блока от
удаления и даёт UI нечего показать как неизменённый контекст.

### D5. Маска разности как фильтр чтения, а не как украшение

Ключевое наблюдение: изменение текста на скане не может не изменить пиксели.
Отсюда отказ от чтения модели для страницы, признанной визуально неизменной,
не способен скрыть правку. Ошибка возможна только в безобидную сторону — лишний
вызов модели.

Поэтому порог выбирается консервативно: жёсткая сторона шкалы. Ложное «изменено»
стоит денег и времени, ложное «не изменено» стоит правды. Для сканов сравнение
выполняется после deskew и перевода в чёрно-белое представление — иначе
неоднородность подложки создаёт различия на всей странице.

Практический выход: документы, совпадающие по тексту и по изображению, не
вызывают модель ни разу. Побочно снимается проблема фантомных изменений —
страница, признанная неизменной, не участвует в текстовом сравнении вовсе.

Альтернатива — выравнивание страниц по текстовым сигнатурам (число строк, длина,
первые N слов, число цифр). Отклонена: требует чтения всех страниц до
выравнивания, то есть не экономит ничего, и хуже переносит сдвиг нумерации
страниц.

### D6. Выравнивание страниц ограничивает размер фрагментов

`find_diffs` вызывается внутри изменённых пар страниц, а не по всему
документу. Это держит фрагменты в пределах одной страницы, поэтому стражи
`MAX_REFINE_PAIRS` и `MAX_INLINE_TOKENS` на сканах не срабатывают.

Альтернатива — плоский diff по всем блокам документа. Отклонена: вставка
страницы или каскад после неё дают фрагмент на десятки страниц, уточнение
пропускается по `MAX_REFINE_PAIRS`, и пользователь видит «изменился весь
документ» без единого сообщения об ошибке.

Номера страниц при этом — только метаданные подписи и они не попадают в текст
сравнения.

### D7. Одна модель на обе роли, разделены только параметры вызова

Разделение выполняется на уровне вызова, а не на уровне модели. `LLM_MODEL`,
`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_EXTRA_BODY` остаются единственными
источниками конфигурации модели; чтение страниц использует их же.

Отдельная конфигурация модели отклонена намеренно: модель одна и та же, а
дублирование её значения в двух наборах переменных создаёт риск молчаливого
расхождения (изменили `LLM_MODEL`, забыли про второй набор переменных —
классификация и
OCR поедут к разным моделям, и расхождение обнаружится только по качеству
чтения сканов).

Что действительно различается между ролями — параметры вызова:

| | классификация фрагмента | чтение страницы |
|---|---|---|
| частота | 1 вызов на фрагмент | 1 вызов на страницу |
| таймаут | 30 с (`llm.py:23`) | больше: страница 8B-модели при 300 dpi может не уложиться |
| thinking | выключается | выключается обязательно |
| объём ответа | одно слово | markdown страницы, 1–2k токенов |
| параллельность | последовательно | нужна, страницы независимы |

Поэтому вводятся настройки роли чтения страниц, а не настройки модели:
`OCR_TIMEOUT`, `OCR_CONCURRENCY`, `OCR_PROMPT_VERSION` (последняя входит в
ключ кэша). `create_chat_model` рефакторится из привязки к префиксу `LLM_` в
функцию с явными параметрами, чтобы роль задавала таймаут и прочие параметры
вызова, не меняя конфигурацию модели.

Если позже понадобится отдельная текстовая модель для классификации, это одна
переменная поверх текущей схемы, и до тех пор её можно не вводить.

Альтернатива — один экземпляр клиента на оба вызова с переопределением модели
на лету. Отклонена: мутация общего состояния между этапами пайплайна не
потокобезопасна.

Мультимодальные content-блоки используются напрямую (`image_url` с data-URI),
отдельный HTTP-клиент не нужен.

### D8. HTML блока строится из нормализованного текста, ответ модели — нет

Ответ модели — источник текста, но не источник разметки. Из markdown
строится текст блока, затем из этого текста собирается HTML по тем же правилам,
что применяет `_wrap_block_html` в `docx_converter.py:130`. Инвариант
`strip_tags(html) == text` проверяется до возврата блока; при невозможности
построить размету блок выдаётся как plain text.

Альтернатива — отдать HTML модели. Отклонена: модель может выдать теги,
расходящиеся с текстом, и клиент молча потеряет форматирование на конкретной
странице. Заодно снимается риск недоверенной разметки: теги строятся
приложением из экранированного текста, набор фиксирован.

### D9. Контракт результата расширяется, а не заменяется

`page` и `crops` — необязательные поля. Существующий код, читающий `text`,
`html`, `images`, не меняется. Свёрнутые диапазоны — отдельные записи в том же
списке строк, а не отдельная структура: клиент уже умеет рисовать строки с
односторонним содержимым, поэтому запись диапазона переиспользует этот механизм.

Альтернатива — отдельное поле `pages[]` в результате. Отклонена: потребовала бы
второго пути отрисовки в клиенте параллельно существующему.

### D10. Кропы — в JSON, с лимитом на документ

Кропы возвращаются как data-URI в составе результата в пределах
настраиваемого лимита; при превышении отбрасываются по убыванию площади, а в
результате ставится признак усечения. Типичный результат — около 1 МБ
(10 страниц × 3 кропа), худший случай без лимита — десятки мегабайт.

Альтернатива — отдельный эндпоинт отдачи кропов. Отклонена для первой версии:
плюс запрос на каждое изображение, кэш и политика очистки на диске, при том
что объём в норме мал. Вернуться к этому варианту, если лимит начнёт
срабатывать на типичных документах.

Важное уточнение к ранней оценке: полноразмерные изображения страниц в
результат не попадают никогда — они нужны только как вход модели и как
источник маски. В payload идут лишь небольшие кропы.

### D11. Рендер через pypdfium2, постранично, в памяти

`pypdfium2` — pip-зависимость с готовыми wheels под Linux x64 и ARM64;
рендер страницы в память, без промежуточных файлов. Для 60 страниц × 2 файла
при 300 dpi это принципиально: одновременный рендер всего документа даёт
порядка 1.5 ГБ.

Альтернатива — `poppler-utils` (`pdftoppm`): результат идентичен, но это
системный пакет, что ломает текущую схему «docker-friendly = только pip» и
требует правки Dockerfile. Побочный плюс pypdfium2 — `pdfplumber` в свежих
версиях умеет рендерить через него же, так что стек остаётся целиком на pip.

### D12. Ветка текстового слоя — детерминированная и бесплатная

При наличии текстового слоя блоки извлекаются через `pdfplumber` без единого
вызова модели. Это не только экономия: требование детерминированной конвертации
(`markdown-conversion/spec.md:25`) на этой ветке выполняется буквально.
Встроенные изображения PDF извлекаются как `images` с подписью содержимого, то
есть замена картинки при неизменном тексте распознаётся уже существующим
механизмом `_mark_images_changed`.

Наличие слоя определяется один раз на документ. Частично заполненный слой
считается присутствующим: решение «доведём ли остальное моделью» требует оценки
качества, а качество субъективно и плохо проверяемо тестом. Оценка качества
скана вынесена за рамки (см. Risks).

### D13. Деградация страницы вместо деградации задачи

Непрочитанная страница даёт пустой список блоков и признак в результате. Если
причина — недоступность модели, в задаче также поднимается признак деградации,
который клиент уже умеет показывать (`app.js:454`).

Альтернатива — падение задачи. Отклонена: пользователь теряет результат
сравнения 40 страниц из-за одной непрочитанной.

### D14. Стратегия кэша по содержимому страницы

Ключ кэша: `sha1(изображения страницы) + имя модели + версия инструкции`.
Одно попадание покрывает три требования: воспроизводимость в пределах кэша,
дешёвое повторное сравнение (при сравнении v2↔v3 переиспользуется прочитанное
ранее) и инвалидация при изменении инструкции без ручной очистки.

Кэш хранится в памяти процесса рядом с хранилищем задач: он уже
in-memory (comparison-jobs), и персистентность не входит в объём — при
перезапуске процесса кэш очищается вместе с задачами.

## Risks / Trade-offs

- **OCR шумит: фантомные изменения на изменённых страницах** → фильтр D4
  снимает шум на неизменённых страницах полностью. На изменённых страницах
  остаётся риск: текстовый diff покажет правку плюс возможные артефакты чтения
  в той же области. Частично компенсируется визуальными кропами, которые
  показывают истинную картину независимо от текста модели.

- **Ошибка чтения на изменённой странице теряет правку молча** → страница
  помечается как не прочитанная, задача — как деградированная, клиент
  показывает уведомление. Но подсветка этой страницы будет пустой, и
  пользователь может не заметить, что на ней что-то было. Смягчение:
  непрочитанные страницы не должны схлопываться как неизменённые — они
  обязаны отображаться как требующие внимания. Это зафиксировано в
  требованиях `page-image-diff`.

- **Шум сканирования съедает порог и ломает выравнивание** → консервативный
  порог и предобработка (deskew, ч/б, морфология) плюс компонентный фильтр по
  площади. Цена — лишние вызовы модели на «чистых» страницах.

- **Страница с таблицей, разорванной границей страниц** → каждая часть
  становится отдельным блоком, таблица в разметке получается незамкнутой.
  Настоящая проблема низкой вероятности и не имеет решения без знания о
  структуре страницы; принимается.

- **Тяжёлые сканы упираются в лимит загрузки** → значение по умолчанию
  `MAX_CONTENT_LENGTH` повышается в `.env.example`; фактический лимит
  остаётся настройкой развёртывания.

- **Реализация порога и морфологии требует внешней библиотеки обработки
  изображений** → сознательно не выбрана на этапе проектирования: добавление
  тяжёлой зависимости — решение уровня задач, а не намерения. Кэш и спеки от
  выбора не зависят. Критерий выбора: BSD/MIT, wheels под ARM64, возможность
  обойтись ею для deskew, порога и связных компонентов.

- **Модель может «перечитать» страницу по-разному при повторе** (батчинг
  vLLM) → кэш скрывает это в пределах процесса, но не между перезапусками.
  Спека фиксирует детерминизм в пределах кэша, а не абсолютную
  воспроизводимость; исходное требование детерминизма в `markdown-conversion`
  неприменимо к ветке чтения моделью и это отражено в дельте спеки.

- **Публикация внутреннего адреса LLM в репозитории** → `.env.example`
  содержит боевой адрес `172.16.48.122:8002` и он уже попал в историю и в
  архивный `proposal.md`. Перенос значения в `.env` не отменяет публикацию;
  изменение `.env.example` на плейсхолдер предотвращает раскрытие внутренней
  топологии в будущих развёртываниях. Ключ `LLM_API_KEY` пуст — решение о
  введении авторизации на эндпоинт принимается вне этого изменения, но
  фиксируется в README как известное ограничение.

## Migration Plan

1. Добавить зависимости `pypdfium2` и `pdfplumber` в `requirements.txt`;
   добавить библиотеку обработки изображений по результату выбора в Risks.
2. Добавить в `create_app` настройки роли чтения страниц и параметров рендера.
   Конфигурация модели не меняется и не дублируется; сравнение `.docx`
   продолжает работать без новых настроек.
3. Включить `.pdf` в `ALLOWED_EXTENSIONS` по умолчанию, повысить
   `MAX_CONTENT_LENGTH` в `.env.example`, заменить боевой адрес LLM на
   плейсхолдер.
4. Подключить конвертер PDF, не меняя выбор ветки на клиенте: пока в
   `ALLOWED_EXTENSIONS` нет `.pdf`, поведение приложения не изменяется.
5. Добавить выравнивание страниц, кропы и свёртывание в пайплайн и клиент.
6. Откат: убрать `.pdf` из `ALLOWED_EXTENSIONS` — приложение возвращается к
   прежнему поведению; код конвертера остаётся неактивным.

## Open Questions

- Качество чтения страниц на конкретных сканах заказчика неизвестно до первой
  выгрузки. Если окажется, что настроенная модель систематически хуже
  детерминированного OCR на сложных страницах, естественное развитие — гибрид:
  модель как основной источник текста, детерминированный OCR как источник
  координат для кропов. Это не меняет спеки и архитектуру (добавляется второй
  источник координат), поэтому вопрос можно решить после измерений на реальных
  файлах.
- Число страниц в типичном документе неизвестно. Влияет только на решение о
  пагинации результата и о целесообразности виртуализации списка строк;
  архитектура от этого не зависит.
