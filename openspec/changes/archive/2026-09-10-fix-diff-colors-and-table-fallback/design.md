# Design: fix-diff-colors-and-table-fallback

## Context

Текущее состояние (см. proposal.md — Why):

- `app/services/jobs.py`, `_build_rows`, табличная ветка (стр. ~168):
  `inline_diff(a, b) or (_plain_segments(a), _plain_segments(b))`.
  `inline_diff` (`app/services/diffing.py:234`) возвращает `None`, когда
  `len(old_tokens) * len(new_tokens) > MAX_INLINE_TOKENS`. Fallback
  подставляет сегменты типа `same` — изменённая ячейка остаётся без
  подсветки, тогда как для обычных блоков fallback (отсутствие `segments`)
  даёт красный/зелёный фон блока через класс `change-changed`.
- Клиент (`app/static/app.js`, `renderTableSide`) уже умеет рендерить
  `cell_segments` любых типов через `appendSegments` → `seg-<type>`.
- `app/static/style.css`: классы подсветки различий (`seg-add`, `seg-del`,
  `seg-add-mark`, `seg-del-mark`, `change-*`, `placeholder-*`) уже
  используют только `--red-light`/`--green-light`/`--green`; жёлтый
  (`--yellow`, `--yellow-light`) встречается только в палитре интерфейса
  (рамки, степпер, уведомление о деградации).
- Жёлтый остался только в комментариях `app/static/app.js:191`
  («изменено — жёлтый») и `tests/test_jobs.py:250` («жёлтый — добавлен»).

## Goals / Non-Goals

**Goals:**

- Fallback изменённой ячейки таблицы даёт красную/зелёную подсветку
  (старая версия — красным в файле 1, новая — зелёным в файле 2).
- Комментарии в коде и тестах описывают двухцветную модель.
- Тесты: fallback таблиц и фиксация двухцветной модели (TDD — сначала
  тесты).

**Non-Goals:**

- Изменение `inline_diff`, ретраев, этапов обработки, парсинга таблиц.
- Изменение клиентского рендеринга (`app.js`/`style.css` функционально не
  меняются — только комментарии; CSS правится лишь при обнаружении
  жёлтого в подсветке различий).
- Остальные замечания REVIEW.md — отдельными change'ами.

## Decisions

### D1. Fallback ячейки — целиком сегменты `del`/`add`

При `inline_diff(a, b) is None` для пары ячеек fallback строит
`([{"text": a, "type": "del"}], [{"text": b, "type": "add"}])` (пустой
текст — пустой список сегментов, как в `_plain_segments`).

Обоснование:

- Контракт данных не меняется: `cell_segments` уже содержит сегменты
  типов `same`/`del`/`add`/`del-mark`/`add-mark`; клиент рендерит
  `seg-del` (красный фон) и `seg-add` (зелёный фон) без правок JS/CSS.
- Подсвечивается только изменённая ячейка, а не вся строка — точнее
  соответствует правилу «изменённая строка — пословной подсветкой внутри
  ячеек», fallback отличается лишь гранулярностью (ячейка целиком).
- Симметрично fallback обычных блоков: там старая сторона красная, новая
  зелёная; здесь то же на уровне ячейки.

Альтернатива: класс `change-changed` на `<tr>` + новые панельные
CSS-правила. Отклонена: подсвечивается вся строка (включая неизменённые
ячейки), требуются правки `app.js` (сейчас класс строки ставится только
при отсутствии `cell_segments`) и `style.css`.

Замечание: `_plain_segments` после исправления может стать неиспользуемой
— удалить вместе с заменой вызова (минимальная правка, не вынося в
отдельный change).

### D2. Двухцветная модель на клиенте — только проверка и комментарии

Аудит CSS показал, что жёлтого в подсветке различий нет. Поэтому работа
на клиенте сводится к: (1) исправлению комментария в `app.js:191` на
двухцветную модель; (2) повторной проверке `style.css`/`app.js` на
отсутствие жёлтого в классах `seg-*`/`change-*`/`placeholder-*` при
реализации.

### D3. Тесты

- **Fallback таблиц**: недоступность пословного diff дёшево эмулируется
  monkeypatch'ем `MAX_INLINE_TOKENS` (или символа `inline_diff` в модуле
  `jobs`) до малого значения — не нужны строки в миллионы токенов. Тест
  строит задачу с изменённой строкой таблицы и проверяет, что
  `cell_segments` изменённой ячейки — `[{"text": ..., "type": "del"}]` /
  `[{"text": ..., "type": "add"}]`, а не `same`.
- **Фиксация двухцветной модели**: тест над результатом задачи (changed +
  removed + added фрагменты) проверяет, что все типы сегментов в
  `segments`/`cell_segments` принадлежат множеству
  `{same, del, add, del-mark, add-mark}` (красные/зелёные типы, без
  `chg`), а значения `change` — `{changed, removed, added, None}`.
- Комментарий `tests/test_jobs.py:250` переписывается под двухцветную
  модель: «зелёный — добавлено, красный — удалено, изменено — пара
  красный (файл 1) + зелёный (файл 2)».

## Risks / Trade-offs

- [Monkeypatch порога в тесте расходится с продовым значением] →
  порог не проверяется, проверяется ветка fallback; значение порога —
  предмет отдельного замечания REVIEW.md (вне области).
- [Удаление `_plain_segments` заденет других вызывающих] → перед
  удалением проверить отсутствие других вызовов (grep); сейчас вызов
  единственный.
- [Пустая сторона пары ячеек (`fillvalue=""`)] → для пустого текста
  fallback даёт пустой список сегментов, поведение добавленных/удалённых
  колонок не меняется (покрыто `test_table_with_different_column_counts`).
