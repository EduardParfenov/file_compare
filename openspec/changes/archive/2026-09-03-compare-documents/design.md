# Дизайн: сравнение двух версий документов

## Context

Текущее состояние — scaffold: фабрика `create_app` с конфигурацией из env,
роуты `/` и `/health`, шаблон-каркас `index.html`. Мотивация и скоуп — в
`proposal.md`, поведенческие контракты — в `specs/`. Ограничения:
Flask dev-сервер (один процесс), конфигурация только через env, тесты без
сети (LLM мокается), docker-friendly относительные пути.

## Goals / Non-Goals

**Goals:**

- Модульный backend: сервисы upload / conversion / diff / llm / jobs,
  тонкие роуты, вся логика тестируется без HTTP и без сети.
- Асинхронная обработка с честными этапными статусами (job + polling
  раз в 3 с).
- Строгий контракт LLM с валидацией, одним ретраем и деградацией до
  классификации по опкодам difflib.
- Vanilla JS frontend без сборщиков.

**Non-Goals:**

- Парсинг `.xlsx` (только точка расширения — реестр конвертеров).
- Персистентность задач/загрузок между перезапусками (in-memory хранилище).
- Аутентификация, многопользовательские сессии, очистка `UPLOAD_DIR` по
  расписанию.
- Dockerfile.

## Decisions

### Архитектура модулей

```
app/
  __init__.py            фабрика create_app (без изменений по сути)
  routes.py              + POST /api/upload, POST /api/compare, GET /api/jobs/<id>
  services/
    uploads.py           save_upload(), get_upload(), реестр загрузок (in-memory)
    conversion.py        convert_to_markdown(path) + реестр конвертеров по расширению
    docx_converter.py    docx → Markdown (python-docx)
    diffing.py           split_blocks(markdown), find_diffs(blocks1, blocks2)
    llm.py               classify_fragment(fragment) → label + флаг semantic
    jobs.py              create_job(), get_job(), run_pipeline() в потоке
  static/
    app.js               загрузка, DnD, запуск compare, polling 3 с, рендер diff
    style.css            палитра (CSS-переменные), спиннер, diff-панели
  templates/index.html   зоны загрузки, кнопка, статус, diff-контейнер
```

### D1: Раздельная загрузка, затем compare по id

`POST /api/upload` сохраняет файл в `UPLOAD_DIR` под `<uuid><ext>` и
возвращает `{"upload_id": "<uuid>", "filename": "..."}`. Реестр
`upload_id → путь` — in-memory словарь. `POST /api/compare` принимает
`{"upload_id_1", "upload_id_2"}`. Альтернатива (один multipart-запрос)
отклонена пользователем; плюс подхода — файл загружается сразу при выборе,
ошибки формата видны до нажатия «Начать сравнение».

### D2: Job + threading + in-memory store

`POST /api/compare` создаёт job (`{"id", "status", "stage", "result",
"error"}`) и запускает `run_pipeline` в `threading.Thread` (daemon).
Flask dev-сервер threaded по умолчанию — этого достаточно для одного
пользователя; Celery/Redis — избыточны на этом этапе. Статусы:
`processing` (stage: `converting` | `diffing` | `llm`), `done`, `failed`.
Сообщения этапов на русском: «Конвертация файлов...», «Поиск различий...»,
«Анализ через LLM...». Клиент опрашивает `GET /api/jobs/<id>` каждые 3
секунды (`setInterval`). Альтернативы: SSE (сложнее тестировать) и
синхронный запрос с имитацией статусов (нечестные статусы) — отклонены.

### D3: Реестр конвертеров

`conversion.py` держит словарь `{".docx": convert_docx}`; единая точка
`convert_to_markdown(path)` выбирает по расширению, иначе —
`UnsupportedFormatError`. `.xlsx` позже добавится одной строкой в реестр.
`docx_converter.py`: заголовки по `paragraph.style.name` (Heading N →
`#`*N), абзацы → текст, таблицы → Markdown-таблицы; блоки разделяются
пустой строкой.

### D4: Diff по блокам Markdown

`split_blocks` делит Markdown по пустым строкам, каждая непустая строка
таблицы — отдельный блок. `find_diffs` — `difflib.SequenceMatcher` над
последовательностями блоков; для опкодов `replace/delete/insert`
формируется фрагмент `{opcode, old_blocks, new_blocks, old_range,
new_range}`. Результат для UI — выровненные пары строк: каждая строка —
`{left: {block, css_class|None}, right: {...}}`, где удалённым/добавленным
блокам соответствует пустое место напротив.

### D5: Контракт LLM и деградация

- Клиент: `langchain-openai` `ChatOpenAI(base_url=LLM_BASE_URL,
  api_key=LLM_API_KEY, model=LLM_MODEL, timeout=30)` — таймаут запроса
  30 секунд (значение предварительное, уточним после прогона против
  реального сервера).
- Системный промпт (рус.): «Ты — классификатор изменений документов.
  Сравни старый и новый фрагменты и ответь строго одним JSON-объектом
  {"label": "changed"|"removed"|"added"} без пояснений». User-сообщение:
  opcode + старый и новый текст фрагмента.
- Парсинг: `json.loads` из ответа (с извлечением JSON из обёртки,
  если модель добавила текст), валидация `label ∈ {changed, removed,
  added}`. Некорректный ответ → ровно 1 ретрай.
- Любой сбой (сеть, таймаут, двойной мусор) → класс по опкоду
  (`replace→changed`, `delete→removed`, `insert→added`), фрагмент и весь
  результат помечаются `semantic=false`. Исключения LLM не пробрасываются
  наружу — job всегда доходит до `done`, если файлы сконвертировались.

### D6: Тестируемость (TDD)

- Сервисы — чистые функции/классы, конфигурация передаётся параметрами.
- LLM инжектируется: `llm.py` принимает chat-модель (или фабрику) —
  в тестах подменяется моком с заранее заданными ответами. Ни один тест
  не ходит в сеть.
- `.docx`-фикстуры генерируются на лету через `python-docx` в `tmp_path`.
- Job-поток в тестах выполняется синхронно (флаг конфига
  `JOBS_SYNCHRONOUS=True` в `create_app` для тестов) — детерминированность
  без `sleep`.

### D7: Зависимости

requirements.txt:

```
Flask==3.1.3
langchain-openai==1.6.0
python-dotenv==1.2.3
python-docx==1.2.0
```

(`openpyxl` осознанно не добавляем — `.xlsx` вне скоупа.)

## Risks / Trade-offs

- [LLM медленно отвечает при большом числе фрагментов] → запросы
  последовательные внутри job-потока, страница не блокируется благодаря
  polling; при необходимости позже — батчинг нескольких фрагментов в один
  запрос (не меняет контракт API).
- [In-memory job/загрузки теряются при перезапуске] → приемлемо для
  одиночной dev-установки; при упаковке в Docker с несколькими воркерами
  понадобится внешнее хранилище (зафиксировано как Non-Goal).
- [Гонки при конкурентном доступе к job store] → dict-операции в CPython
  атомарны; запись результата — одна операция присваивания. Достаточно для
  dev-режима.
- [Модель оборачивает JSON в пояснения] → извлечение первого JSON-объекта
  из текста + ретрай + деградация как крайний случай.
- [Накопление файлов в UPLOAD_DIR] → Non-Goal; позже — очистка по TTL.
