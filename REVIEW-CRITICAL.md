# Критичные замечания к проекту file_compare

Дата: 2026-09-29

## 1. In-memory хранилища не потокобезопасны и не переживают перезапуск

**Файлы:** `app/services/uploads.py:10`, `app/services/jobs.py:26`

`_UPLOADS` и `_JOBS` — обычные dict без блокировок. При одновременных запросах возможны race conditions. При перезапуске все данные теряются: загруженные файлы остаются на диске, но их upload_id больше не найти; результаты сравнений теряются.

**Риск:** Потеря данных, некорректные результаты при нагрузке.

**Рекомендация:** Заменить на Redis/PostgreSQL или добавить `threading.Lock` для минимальной защиты.

---

## 2. Нет проверки типа файла (только расширение)

**Файл:** `app/services/uploads.py:22-25`

Проверяется только расширение файла. Файл `evil.docx` с произвольным содержимым пройдёт валидацию. Если файлы будут скачиваться пользователями или передаваться в другие системы — это уязвимость.

**Риск:** Загрузка вредоносных файлов, потенциальная XSS через скачивание.

**Рекомендация:** Проверять magic bytes (сигнатуру файла) для поддерживаемых форматов.

---

## 3. Нет rate limiting

**Файл:** `app/routes.py`

Любой, кто имеет доступ к серверу, может загружать файлы и запускать сравнения без ограничений. Это вектор для DoS.

**Риск:** DoS-атаки.

**Рекомендация:** Добавить rate limiting (например, Flask-Limiter).

---

## 4. Клиентская часть без тестов

**Файлы:** `app/static/app.js`, `app/templates/index.html`, `app/static/style.css`

Вся логика рендера (вплетение diff в HTML, таблицы, синхронный скролл, выравнивание высот) не покрыта тестами. Это самая хрупкая часть приложения — изменения в конвертере или diff-алгоритме могут сломать отображение без обнаружения.

**Риск:** Регрессии в UI, которые не будут пойманы тестами.

**Рекомендация:** Добавить тесты для клиента (jsdom или playwright) для ключевых сценариев рендера.
